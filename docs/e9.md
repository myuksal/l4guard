# 부하·장애·우회 검증

이 문서는 운영 투입 전 필수 시험인 E9의 절차, 자동화 자산, 통과 기준,
측정 결과를 정리한다. 설계 기준은 `plan.md` 10·11장, 작업 정의는
`workflow/epic.md`의 E9를 따른다.

## 1. 자동화 자산

| `scripts/e9-verify.py bypass` | E9-T3 manifest 감사, IPv6, UDP |

건너뛸 수 있다.

## 2. E9-T1 연결 폭주

### 시험 방법

`scripts/e9-verify.py load`는 다음을 수행한다.

1. 로컬 echo upstream과 Guard를 띄운다.
2. `max_connections = 32`, `max_sessions = 32`로 제한한다.
3. 256개 연결을 동시에 연다.
4. `l4guard_active_sessions`, `l4guard_accepted_total`,
   `l4guard_rejected_total{reason="budget"}`, `l4guard_ip_entries`를 읽는다.
5. 프로세스 FD 수와 RSS를 baseline과 비교한다.
6. 모든 client를 닫고 세션·FD가 baseline으로 돌아오는지 확인한다.

### 통과 기준

- `active_sessions`가 `max_connections`를 넘지 않는다.
- 승인된 세션 수가 상한을 넘지 않는다.
- 초과 연결이 예산 사유로 거절된다.
- IP별 상태 맵 항목 수가 `max_ip_entries`를 넘지 않는다.
- FD 수가 `baseline + 2 × max_connections + 여유` 안에 있다.
- RSS가 256 MiB 미만이다.
- 연결을 닫으면 active session과 FD가 회수된다.

### 측정 결과

이 환경(macOS, debug 바이너리)에서 256개 연결 폭주 시:

```text
active=32 accepted=32 rejected_budget=224 ip_entries=1
fds=75/11 rss_kib=6288/5312
```

- task는 승인된 세션에만 1개씩 생긴다. 거절된 연결은 task를 만들지 않는다.
- 세션 registry와 IP 상태 맵은 각각 32, 16 상한 안에 머문다.
- FD는 세션당 client socket과 upstream socket 2개 수준으로 증가하고,
  연결을 닫으면 baseline 근처로 돌아온다.
- debug 빌드 RSS는 약 6 MiB다. release 이미지의 64MiB request/256MiB
  limit 안에 충분히 들어간다.

운영 환경에서는 `scripts/e9-verify.py load`를 Guard 이미지에 대해 실행하고,
cgroup memory, socket memory, conntrack도 함께 기록한다. RSS만으로 자원
예산을 확정하지 않는다.

## 3. E9-T2 긴급 차단

### 시험 방법

`scripts/e9-verify.py emergency`는 다음을 확인한다.

1. 정상 세션을 하나 연다.
2. 설정을 `policy.emergency_block = true`로 바꾸고 `SIGHUP`을 보낸다.
3. 기존 세션이 닫히고 `l4guard_cancelled_total`이 증가하는지 확인한다.
4. 새 연결이 즉시 닫히고
   `l4guard_rejected_total{reason="policy"}`가 증가하는지 확인한다.
5. `emergency_block = false`로 되돌려 정상 연결이 복구되는지 확인한다.
6. `listeners[].enabled = false`로 listener를 중지해 기존 세션이 닫히고
   새 연결이 `reason="stopped"`로 거절되는지 확인한다.
7. listener를 다시 켜서 연결이 복구되는지 확인한다.

### 통과 기준

- 긴급 차단은 신규 연결과 기존 연결 모두에 적용된다.
- listener 중지도 신규 연결과 기존 세션 모두에 적용된다.
- 정책 버전이 reload 전후로 바뀌고, 원래 설정으로 돌리면 같은 버전으로
  돌아온다.
- 복구 후 정상 echo가 다시 동작한다.

### 측정 결과

```text
PASS emergency: existing sessions cancelled, new connections rejected,
listener stop and resume applied
```

## 4. E9-T3 우회 차단

### Manifest 감사

`scripts/e9-verify.py bypass`는 `kubectl kustomize`로 렌더링한 자산을
검사한다.

- backend Service는 `ClusterIP`이고 `NodePort`/`LoadBalancer`가 아니다.
- backend와 Guard 어디에도 `hostPort`가 없다.
- 공개 P2P/RPC Service는 `LoadBalancer`와
  `externalTrafficPolicy: Local`을 사용한다.
- 사설 P2P/RPC Service는 `ClusterIP`다.
- backend NetworkPolicy egress에 `0.0.0.0/0` 또는 `::/0` 기본 경로가 없다.
- Guard NetworkPolicy는 backend 네임스페이스에서 오는 31001/32001만
  사설 ingress로 허용한다.

### IPv6

Guard를 `[::1]:port`에 bind하고 `::1/128` allow/deny를 reload한다.

- IPv6 allow 상태에서 echo가 동작한다.
- `deny = ["::1/128"]` reload 시 기존 IPv6 세션이 닫히고 새 연결이
  `reason="policy"`로 거절된다.
- deny를 제거하면 IPv6 연결이 복구된다.

### UDP

Guard listener는 TCP만 bind한다. 같은 포트로 UDP datagram을 보내도
세션이 생기지 않고 upstream에 도달하지 않는다. Geth discovery처럼 UDP가
필요한 경로는 이 버전에서 지원하지 않으며, `--nodiscover`로 직접 탐색을
꺼야 한다.

### Cluster 수준 확인

NetworkPolicy와 LB 설정은 로컬 harness만으로 완전히 검증할 수 없다.
운영 클러스터에서 다음을 별도로 확인한다.

```sh
# backend 직통: 외부/다른 네임스페이스에서 실패해야 한다.
kubectl -n default run bypass --rm -it --image=busybox -- \
  nc -vz blockchain-node.blockchain.svc.cluster.local 26656

# backend에서 인터넷 직통: 실패해야 한다.
kubectl -n blockchain exec deploy/backend -- \
  nc -vz 1.1.1.1 443

# outbound 직접: backend가 실제 peer로 직접 연결하지 못해야 한다.
kubectl -n blockchain exec deploy/backend -- \
  nc -vz <peer-public-ip> 26656

# Guard 사설 경로: 성공해야 한다.
kubectl -n blockchain exec deploy/backend -- \
  nc -vz l4guard-private.l4guard.svc.cluster.local 31001
```

하나라도 예상과 다르면 배포를 중단하고 `deploy/backend/networkpolicy.yaml`,
LB target group, backend Service type을 점검한다.

### 측정 결과

```text
PASS manifests: backend stays ClusterIP, public services use
externalTrafficPolicy Local, backend egress has no default route
PASS ipv6: IPv6 allow/deny reaches new and existing sessions
PASS udp: UDP datagrams to the TCP listener are not relayed
```

## 5. E9-T4 Guard 교체

### 시험 방법

`scripts/e9-verify.py replace`는 다음을 수행한다.

1. 별도 프로세스인 counter backend를 띄우고 데이터 파일에 카운터를 쓴다.
2. Guard를 통해 `inc`를 보내 `1`을 받는다.
3. Guard를 `SIGKILL`로 종료한다.
4. backend 프로세스와 데이터 파일이 그대로인지 확인한다.
5. 같은 포트에 새 Guard를 띄운다.
6. client가 재접속해 `inc`를 보내 `2`를 받는지 확인한다.
7. Guard 종료부터 재접속 성공까지 시간을 기록한다.

### 통과 기준

- Guard가 죽어도 backend 프로세스가 살아 있다.
- backend 데이터가 유지된다.
- 같은 공개 endpoint로 재접속할 수 있다.
- 재접속 후 새 Guard를 통해 요청이 처리된다.

### 측정 결과

```text
PASS replace: backend process and data survived; reconnect took 0.068s
```

로컬 loopback 시험은 재접속 자체를 증명한다. Kubernetes에서는
`maxSurge: 0`, `maxUnavailable: 1` rolling update와 `preStop` 지연 때문에
Pod 교체 시간이 더 길다. 실제 체인 회복은 다음 절차로 측정한다.

## 6. E9-T5 회복 측정

### 시험 방법

`scripts/e9-cometbft-recovery.sh`는 E8의 CometBFT block sync harness를
확장한다.

1. validator(node-a)와 full node(node-b)를 만들고, node-b를 Guard의 고정
   egress listener에 연결한다.
2. node-b가 chain tip에 도달하면 baseline height/peer 수를 기록한다.
3. Guard를 제거하고 peer가 끊기는 시간을 잰다.
4. 기본 3초 동안 Guard를 내려 두고, Guard를 통한 RPC `/status` 성공률을
   측정한다.
5. 같은 설정으로 replacement Guard를 띄운다.
6. peer 재접속 시간과 node-a tip 대비 2블록 이내 회복 시간을 잰다.
7. replacement Guard metrics에서 `accepted`, `active_sessions`를 확인한다.

### 측정 결과 예시

```text
baseline: node-b height=25 peers=1
node-b lost its peer after 0.215s
holding the guard down for 3s
node-b reconnected to the replacement guard after 3.968s
PASS recovery:
  guard outage before replacement: 2.871s
  peer reconnect: 3.968s
  head lag recovery (within 2 blocks): 5.862s
  total outage to head lag recovery: 8.826s
  RPC success during outage/recovery: 22/33 (66.7%)
  replacement guard accepted=23 active_sessions=1
  node-b height=33 peers=1
```

수치는 환경과 chain block time에 따라 달라진다. 중요한 것은 다음 세 가지를
**별도로** 기록하는 것이다.

- peer 수 회복 시간
- head lag 회복 시간
- Guard 경유 RPC 성공률 회복 시간

validator에 적용하기 전에는 비서명 full node에서 같은 측정을 반복한다.

## 7. E9-T6 RPC 정책 우회

### 시험 방법

`scripts/e9-verify.py rpc-bypass`는 L7 listener 앞에서 다음 요청을 보내고
upstream 도달 여부를 확인한다.

| 형태 | 기대 |
|---|---|
| `GET /status` | 200, upstream 도달 |
| `GET /%73tatus` | 400, upstream 미도달 |
| `GET //status` | 400, upstream 미도달 |
| `GET http://node/status` | 400, upstream 미도달 |
| `GET /status/` | 400, upstream 미도달 |
| `GET /debug_traceCall` | 403, upstream 미도달 |
| batch 안에 금지 method 포함 | 403, upstream 미도달 |
| 중복 `method` key | 400, upstream 미도달 |
| escape로 만든 금지 method | 403, upstream 미도달 |
| `Upgrade: websocket` | 400, upstream 미도달 |
| `Content-Encoding: gzip` | 415, upstream 미도달 |
| `Content-Length` + `Transfer-Encoding` | 400, upstream 미도달 |
| escape로 만든 허용 method | 200, upstream 도달 |
| chunked body의 허용 method | 200, upstream 도달 |

핵심은 **raw substring match가 아니라 JSON escape를 디코드한 뒤 정확히
비교**한다는 점이다. `\u0073tatus`는 `status`로 디코드되어 허용되고,
`debug_trace\u0043all`은 `debug_traceCall`로 디코드되어 거부된다. upstream이
실행하는 method와 Guard가 판단한 method가 같다.

### 통과 기준

- 거부된 형태는 upstream 연결을 열지 않는다.
- 허용된 형태만 upstream에 도달한다.
- `l4guard_l7_rejected_total`의 `policy`, `json`, `upgrade`, `encoding`,
  `malformed` 카운터가 증가한다.

### 측정 결과

```text
PASS rpc-bypass: batch, escape, duplicate-key, URI, encoding, and Upgrade
shapes were rejected before the upstream
```

같은 경계는 `src/l7.rs`와 `src/relay.rs`의 단위 테스트로도 고정되어 있다.
WebSocket은 이 버전에서 지원하지 않으며, L7 listener는 Upgrade를 거부한다.

## 8. E9-T7 복제본 일관성

### 시험 방법

`scripts/e9-verify.py replicas`는 세 Guard를 띄운다.

1. A와 B는 같은 정책, C는 `emergency_block = true`다.
2. A와 B의 `l4guard_policy_version`이 같은지 확인한다.
3. C의 버전이 다른지 확인한다.
4. A를 C와 같은 정책으로 reload해 버전이 같아지는지 확인한다.
5. B를 재시작해 같은 정책 버전이 유지되는지 확인한다.

### 통과 기준

- 같은 입장 관련 설정을 쓰는 복제본은 재시작 여부와 관계없이 같은 버전을
  보고한다.
- 정책이 바뀌면 버전이 바뀐다.
- listener 순서, allow 목록 순서, metrics 주소, listen 포트는 버전을 바꾸지
  않는다.

### 측정 결과

```text
PASS replicas: identical policies share a version, a changed policy differs,
and a restart preserves the version
```

운영에서는 모든 Guard의 `/metrics`에서 `l4guard_policy_version`을 수집해
같은 값인지 확인한다. 다르면 ConfigMap 반영 상태와 reload 로그를 확인한다.

## 9. E9-T8 Canary

### 순서

1. **사전 점검**
   - `make check`와 `make e9-check` 통과
   - 대상 Guard 이미지 digest 고정
   - backend Service `ClusterIP`, LB target Guard 전용, NetworkPolicy 적용
   - `/metrics`에서 모든 Guard의 `l4guard_policy_version` 동일
   - backend와 Guard의 readiness가 서로를 기다리지 않음
2. **비서명 full node**
   - validator key가 없는 full node에 Guard를 먼저 적용한다.
   - 최소 30분 동안 peer 수, head lag, RPC 성공률, Guard rejection 사유를
     기록한다.
   - `make e9-recovery`와 같은 교체 시험을 한 번 수행한다.
3. **validator**
   - 한 번에 하나의 validator만 적용한다.
   - `maxSurge: 0`, `maxUnavailable: 1`과 PDB `minAvailable: 1`을 유지한다.
   - 교체 중 peer 수와 head lag가 회복되는지 확인한다.
4. **전체 적용**
   - 모든 validator에 적용한 뒤 24시간 관측한다.
   - `l4guard_rejected_total`의 사유별 추이와 `l4guard_active_sessions`를
     baseline과 비교한다.

### Rollback

- 긴급 차단: `policy.emergency_block = true`로 reload
- 특정 listener만 차단: `listeners[].enabled = false`로 reload
- 설정 오류: 마지막 정상 ConfigMap으로 되돌리고 reload
- Guard 자체 문제: 이전 이미지 digest로 rolling update
- backend 직통 경로를 열어서는 안 된다. rollback 중에도 backend Service는
  `ClusterIP`를 유지한다.

### Canary 체크리스트

- [ ] 비서명 full node에서 먼저 검증했다.
- [ ] peer 수 회복 시간을 기록했다.
- [ ] head lag 회복 시간을 기록했다.
- [ ] Guard 경유 RPC 성공률 회복 시간을 기록했다.
- [ ] 모든 Guard의 정책 버전이 같다.
- [ ] 긴급 차단과 listener 중지를 실제로 시험했다.
- [ ] backend 직통·outbound 직접·IPv6·UDP 경로를 확인했다.
- [ ] rollback 절차를 문서와 함께 리허설했다.

## 11. 남은 운영 확인

- **Geth snap sync:** 상태가 있는 peer가 필요하므로 운영 환경에서
  `docs/e8.md` 7장 절차로 확인한다.
- **Cluster 수준 우회:** NetworkPolicy와 LB는 실제 CNI/클라우드에서
  4장의 명령으로 확인한다.
- **PROXY protocol:** 이 버전은 수신하지 않는다. `externalTrafficPolicy:
  Local`과 비종단 L4 LB를 유지한다.
- **UDP discovery:** 지원하지 않는다. Geth는 `--nodiscover`와 static peer를
  사용한다.
