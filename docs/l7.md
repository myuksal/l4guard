# HTTP L7 검사

이 문서는 `l4guard`의 선택적 HTTP/1.1 JSON-RPC 검사 기능을 운영자 관점에서
설명한다. 설계 기준은 `plan.md` 7장, 작업 정의는 `workflow/epic.md`의 E6을
따른다. L7은 listener별로 켜고 끌 수 있으며, 켜지 않은 listener는 기존처럼
바이트를 그대로 중계한다.

## 1. 범위

L7 listener는 **연결마다 HTTP/1.1 요청 하나**를 파싱한다.

1. 요청 head를 크기·개수·수신 시간 상한 안에서 읽는다.
2. `GET` 또는 `POST`만 허용하고, hop-by-hop·압축·Upgrade를 거부한다.
3. body를 누적 크기·수신 시간 상한 안에서 읽는다.
4. JSON-RPC method를 정확히 비교해 allowlist와 deny 목록을 적용한다.
5. 비싼 method의 요청률과 동시 실행량을 **전송 전에** 차감한다.
6. 모든 검증을 통과한 요청만 새 요청으로 다시 만들어 upstream에 보낸다.
7. upstream 응답은 그대로 client로 흘려보낸다.

응답은 검사하지 않는다. L7은 backend 응답 파서의 취약점을 대신 처리하는
계층이 아니라, **backend에 도달하는 요청의 형태와 양을 제한하는 계층**이다.

## 2. 설정

```toml
[[listeners]]
name = "rpc-public"
listen = "0.0.0.0:26657"
mode = "inbound"
upstream = "rpc-node"

[listeners.l7]
max_header_bytes = 16384
max_header_count = 64
header_timeout_ms = 5000
max_body_bytes = 1048576
body_timeout_ms = 10000
max_json_depth = 32
max_json_array = 256
max_batch = 32
allow_methods = ["eth_call", "eth_getLogs", "eth_blockNumber", "status"]
deny_methods = ["debug_traceCall"]

[listeners.l7.expensive_methods.eth_call]
rate_per_second = 20
concurrent = 8

[listeners.l7.expensive_methods.eth_getLogs]
rate_per_second = 10
concurrent = 4
```

| 설정 | 기본값 | 의미 |
|---|---|---|
| `max_header_bytes` | 16384 | 요청 head 최대 바이트. 상한 1 MiB |
| `max_header_count` | 64 | header 최대 개수. 상한 256 |
| `header_timeout_ms` | 5000 | head 수신 시간 상한 |
| `max_body_bytes` | 1048576 | 디코딩된 body 최대 바이트. 상한 16 MiB |
| `body_timeout_ms` | 10000 | body 전체 수신 시간 상한 |
| `max_json_depth` | 32 | JSON 중첩 깊이. 상한 128 |
| `max_json_array` | 256 | 임의 배열 원소 수와 객체 key 수 상한 |
| `max_batch` | 32 | batch 항목 수 상한. `max_json_array` 이하 |
| `allow_methods` | `[]` | 허용 method. 비어 있으면 **모두 거부** |
| `deny_methods` | `[]` | 항상 거부하는 method. allow보다 우선 |
| `expensive_methods` | `{}` | method별 요청률·동시 실행량 |

`allow_methods`가 비어 있으면 fail-closed로 모든 요청이 거부된다. L7을 켠 뒤
허용할 method를 반드시 명시한다.

`listeners[].l7`은 **재시작 대상**이다. 변경하면 `SIGHUP` reload는 거부되고
마지막 정상 설정이 유지된다. 다만 `policy.emergency_block`은 reload 가능하며,
L7 listener의 기존 세션도 즉시 취소한다.

## 3. Method 정책

- method 이름은 JSON escape를 **디코딩한 뒤** 정확히 비교한다. `"\u0065th_call"`
  은 `eth_call`로 해석되어 allowlist와 비교된다.
- 부분 문자열 검색은 사용하지 않는다. `eth_call_debug_trace`나
  `x_debug_traceCall`은 allowlist에 없으므로 거부된다.
- `deny_methods`는 allowlist보다 우선한다.
- `policy.emergency_block`이 켜져 있으면 L7 요청도 거부된다.

### GET URI 호출

CometBFT는 같은 method를 `GET /method?param=...` 형태로도 노출한다. L7은
경로 segment를 method 이름으로 사용한다.

```
GET /status?height=1   -> method "status"
GET /debug_trace       -> method "debug_trace"
```

경로는 `/[A-Za-z0-9_]+` 형태만 허용한다. `//`, `..`, `%xx`, fragment, 빈
경로는 parser 차이를 만들 수 있으므로 거부한다.

### POST와 URI 경로

POST에 비어 있지 않은 경로가 있으면 **경로 method와 body method를 모두**
검사한다. 예를 들어 `POST /status`에 `{"method":"debug_traceCall"}`을 보내면
두 method가 모두 allowlist에 있어야 한다. 어느 한쪽도 backend의 해석을
가정하지 않는다. body가 없는 URI POST는 경로 method만 검사한다.

## 4. JSON 검사

- 요청은 JSON-RPC 객체 하나 또는 batch 배열이다. 빈 batch는 거부한다.
- batch는 **모든 항목**을 검사하고, 항목 수는 `max_batch`로 제한한다.
- 객체와 배열은 `max_json_array`, 중첩은 `max_json_depth`로 제한한다.
- 같은 객체 안의 중복 key는 거부한다. `method`, `params`, `jsonrpc`, `id`처럼
  보안 판단에 쓰이는 key의 모호한 중복을 허용하지 않기 위해서다.
- `method`는 문자열이어야 하며 128바이트 이하의 printable ASCII다.

## 5. 비싼 method

`eth_call`, `eth_getLogs`처럼 허용된 method도 backend 비용이 클 수 있다. L7은
**보내기 전에** method별로 다음을 차감한다.

- `rate_per_second`: listener별 token bucket. burst는 `rate_per_second`와 같다.
- `concurrent`: 동시에 실행 중일 수 있는 요청 수.

동시 실행 permit은 upstream 응답이 끝날 때까지 유지된다. batch는 항목마다
token과 permit을 하나씩 차감하며, 하나라도 부족하면 batch 전체를 거부한다.
이미 차감한 token은 반환하지 않는다(보수적).

## 6. 거부와 응답

| 사유 | HTTP 상태 | 의미 |
|---|---|---|
| `malformed` | 400 | 요청 line·framing·중복 header 오류 |
| `header` | 431 | head 크기·개수 상한 초과 |
| `body` | 413 | body 크기 상한 초과 |
| `timeout` | 408 | head·body 수신 시간 초과 |
| `method` | 405 | `GET`/`POST` 이외의 method |
| `encoding` | 415 | 압축 body 또는 `chunked` 이외 transfer coding |
| `upgrade` | 400 | `Upgrade` header 또는 `Connection: upgrade` |
| `json` | 400 | JSON-RPC 형식·깊이·배열·중복 key·batch 위반 |
| `policy` | 403 | method 정책 또는 긴급 차단 |
| `quota` | 429 | method별 요청률·동시 실행량 초과 |

거부 응답은 짧은 plain text이며 `Connection: close`를 포함한다. 거부 직후
client가 아직 보내는 중인 바이트를 잠시 drain해, 응답 대신 TCP reset이
나타나는 일을 줄인다.

## 7. 전달 방식과 제약

- 검증이 끝난 요청은 **새로 만든 요청**이다. client의 header를 그대로
  복사하지 않는다.
- 전달하는 header는 `Host`, `Content-Type`, `Content-Length`, `Accept`,
  `Connection: close`로 제한한다. `X-Forwarded-For`, `Upgrade`,
  `Content-Encoding`, `Transfer-Encoding` 등은 전달하지 않는다.
- `chunked` body는 디코딩한 뒤 `Content-Length`로 다시 만든다.
- `Expect: 100-continue`는 지원한다. 그 외 `Expect` 값은 거부한다.
- upstream 요청은 `Connection: close`이므로 연결마다 요청 하나를 처리한다.
  keep-alive 다중 요청은 지원하지 않는다.
- 이미 보낸 요청을 자동으로 다시 보내지 않는다.
- WebSocket JSON-RPC는 **명시적으로 미지원**이다. `Upgrade` 요청은 tunnel하지
  않고 거부한다.
- 응답 크기나 응답 시간에는 별도 상한을 두지 않는다. L4 세션과 마찬가지로
  장기 연결을 허용하며, 필요하면 upstream·client 양쪽의 timeout으로 제한한다.

## 8. 지표와 로그

L7 listener는 다음 지표를 추가로 노출한다.

| 지표 | 의미 |
|---|---|
| `l4guard_l7_requests_total` | 검사한 HTTP 요청 수 |
| `l4guard_l7_forwarded_total` | upstream으로 전달한 요청 수 |
| `l4guard_l7_rejected_total{reason="..."}` | 사유별 거부 수 |

거부 로그는 `listener`, `peer`, `reason`, `version` 필드를 사용하며 메시지는
`rpc request rejected`로 같다. `reason` 값은 6장의 사유와 같다. 요청 body,
method 인자, header 값은 로그에 남기지 않는다.

## 9. 회귀 시험

다음 우회 형태를 테스트로 고정한다.

- batch 안에 숨긴 거부 method
- JSON escape·유니코드 변형 method
- 중복 `method` key
- `//`, `..`, `%xx`, fragment가 섞인 URI
- 거대 header와 거대 body
- `Content-Length`와 `Transfer-Encoding` 동시 사용
- `Upgrade`·`CONNECT`·압축 body
- `"debug_"` 부분 문자열 검색에 의존하지 않는지
